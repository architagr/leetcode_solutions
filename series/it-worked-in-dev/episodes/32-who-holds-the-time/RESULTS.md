# Measured

```
Apple M1 Pro · go1.26.4 darwin/arm64
go test -bench=. -benchtime=100x -count=3              (median of three)
go test -bench=/request -benchtime=20000x -count=3     (median of three)
go test -run TestSteps -v
```

Reproduce with the commands above in this directory. `request` is fast enough
that 100 iterations is noise; its rows use the 20,000-iteration run.

Every trace is generated by `walk` or `chain` in `profile_test.go`. `walk`
calls or returns at random, capped at a maximum depth, with 20 to 2,000 ns
between events. `request` is one HTTP request, twelve layers at most; `batch`
is a long batch job with the same shallow shape; `parser` is a recursive-descent
parser on nested input, allowed to go 4,000 deep and drifting down to 1,638;
`recursion` is one function recursing 5,000 deep and unwinding.

`TestSteps`, how many spans the per-call inner loop reads in total:

```
request       2000 calls, max depth    12  |  spans the inner loop reads:       11039
batch       200000 calls, max depth    16  |  spans the inner loop reads:     1511720
parser       20000 calls, max depth  1638  |  spans the inner loop reads:    15077280
recursion     5000 calls, max depth  5000  |  spans the inner loop reads:    12497500
```

`parser` has a tenth of `batch`'s calls and makes the inner loop read 9.97
times as many spans.

## Time

| shape | calls | max depth | spans, then direct callees | stack replay | ratio |
|---|---:|---:|---:|---:|---:|
| `request` | 2,000 | 12 | 24.3 µs | 5.86 µs | 4.15x |
| `batch` | 200,000 | 16 | 4.27 ms | 1.56 ms | 2.73x |
| `parser` | 20,000 | 1,638 | 12.5 ms | 151 µs | 82.3x |
| `recursion` | 5,000 | 5,000 | 8.20 ms | 26.7 µs | 307x |

Raw ns: 24,302 / 5,860 · 4,270,666 / 1,564,211 · 12,457,010 / 151,339 ·
8,198,515 / 26,736

`parser` against `batch`, spans version: 20,000 calls take **2.92x** as long as
200,000. Per call the spans version costs 12 ns on `request`, 21 ns on `batch`,
623 ns on `parser` and 1,640 ns on `recursion`; the stack replay costs 3 to 8 ns
per call on all four.

## Allocated, same runs

The spans version builds one 32-byte span per call before it can start, plus
the stack of open calls. The replay allocates only its stack, which grows past
its initial 64 entries on the two deep traces.

| shape | spans, then direct callees | stack replay |
|---|---:|---:|
| `request` | 65.6 KB | 64 B |
| `batch` | 6.41 MB | 64 B |
| `parser` | 686 KB | 38.6 KB |
| `recursion` | 291 KB | 127 KB |

Raw bytes: 65,600 / 64 · 6,406,212 / 64 · 685,760 / 38,592 · 291,136 / 127,296

The 64 B in every replay row is the result itself: eight int64s, one per
function. The spans version allocates the same 64 B on top of its spans.
